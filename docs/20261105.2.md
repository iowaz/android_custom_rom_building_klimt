## The SELinux warning

Duck Detector on 20261105 (`diagnostics/detectors/20261105-115132-fenrir`, private) rated SELinux DANGER:
"Enforcing with recognized privileged contexts". Two observations came from the build's policy:

- a DirtySepolicy-style access query reports `adbd -> adbroot binder call` as allowed;
- writing `u:r:adbroot:s0` to `/proc/self/attr/current` from its app_zygote carrier fails with EACCES (13), where
  an unknown context gives EINVAL (22) like the KernelSU, Magisk and LSPosed probes did.

Both come from LineageOS's adb root policy in `device/lineage/sepolicy`, which goes into every variant although
`vendor/lineage/config/common.mk` installs `adb_root` only on non-user builds with `WITH_SU=true`. evox21 to
evox31 gated the rules (evox21 scan: `adbd -> adbroot` denied); the gate was dropped with the forks on
2026-11-04, so 20261104 and 20261105 had the rule again.

Fix: device patch `device/lineage/sepolicy` `0001` "sepolicy: Keep the adb root policy and domain to debuggable
builds" (class `personal`, device `45ad45b`). Unlike the evox21 gate it also declares the `adbroot` domain only in
userdebug and eng builds, so the context does not exist on a user build. The `adbroot_exec`, `adbroot_data_file`
and `adbroot_service` types stay, because `file_contexts` and `service_contexts` label with them.

Checked before the build with the 20261105 ninja graph on the SELinux intermediates only (no `m`, staging
unchanged; `diagnostics/builds/20261105.2/POLICY_CHECK.md`): the neverallow, `sepolicy_test`, dev-type and
treble tests (31.0 to 202504) pass; the user policy loses the `adbroot` type, its 24 allow rules, one dontaudit,
init's type transition and one generated neverallow, and nothing else.
