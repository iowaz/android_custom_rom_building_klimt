# Media volume and wireless Android Auto

The owner reports large low-volume changes on the phone speakers, and Spotify momentarily stopping
and becoming audible on the phone during notifications over wireless Android Auto. Music resumes.
These are separate issues. No phone was connected to adb during the source investigation.

## Next-build volume change

Device base: `1b1b1cc` on `cnb`; local volume commit: `3296844`. Framework AudioService has 15 media steps unless
`ro.config.media_vol_steps` overrides it. klimt declares Xiaomi's
`ro.vendor.audio.media.volume.steps=30` and `ro.vendor.audio.media_vol_stepless=30`, but neither
property configures upstream AudioService. The packaged 20261108 system and vendor build properties
also lack the framework override.

Set `ro.config.media_vol_steps=30` in the device's system properties. Change
`ro.config.media_vol_default=20` to `10`: 20 was invalid with a maximum of 15, so AudioService
used its fallback of 5/15. The new 10/30 default keeps the same fraction for devices without a saved
media volume. Existing saved per-device indices are not migrated; check the volume after updating.

The shipped XML speaker/media curve uses (index, millibels): (1,-5800), (20,-4000), (60,-1700),
(100,0). Audio policy interpolates in decibels, then converts to amplitude. It is already nonlinear
in amplitude. The first two positive framework indices map to approximately -53.3 and -46.6 dB with
15 steps, versus -56.1 and -53.3 dB with 30. This calculation is from VolumeCurve.cpp, not an
acoustic measurement. The framework range is shared across media routes, so headphones/Bluetooth
also gain finer indices; the device-category curves, maximum gain, alarms and calls are unchanged.

This corrects a concrete framework/vendor configuration mismatch. HyperOS can add proprietary
gain and volume handling, so identical stock slider behavior is not established. Dolby processing
can change perceived loudness independently of the slider; active Dolby settings were not read.
Compare the first few speaker steps with Dolby enabled and disabled after the next build boots.
No Dolby, amplifier calibration or shared audio-policy curve is changed here.

## Android Auto remains open

NotificationAttentionHelper.playSound already checks the relevant stream volume before calling
the ringtone player. AudioService.getStreamVolume returns zero for a muted stream, and
shouldNotificationSoundPlay also checks this. Therefore source inspection does not demonstrate that
ordinary muted notifications are starting the player. NotificationPlayer requests transient focus
for sounds it actually receives; Android Auto and apps can also request focus independently.

Music becoming audible on the phone makes a route transition a plausible explanation, but there is
no contemporaneous audio focus, device connection or audio-policy evidence. Do not disable A2DP
offload, remove routes, change the stock notification.single property, bypass all notification focus
or suppress navigation/calls on this evidence alone. No Android Auto fix is claimed or applied.

Capture the fault while parked, with USB adb connected and wireless projection active:

```powershell
pwsh -File .\repositories\android_custom_rom_building_klimt\build-setup\windows\capture-audio.ps1
```

The script records 45 seconds of main/system logcat plus before/during/after audio service, policy,
flinger and media-session dumps in `diagnostics/audio/<timestamp>/private/`. It does not clear logs,
change settings, inject notifications, request root or reboot. Raw files may contain private app
metadata and device addresses; keep them local. Notify once during the window using the same app
that normally triggers the problem. Inspect the focus requester/gain, A2DP suspension/connection,
remote-submix policy mixes and Spotify output devices at the event before selecting the fix.
